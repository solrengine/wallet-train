# feat: Build PiggyBank Rails app with solrengine gems

## Overview

Build a Rails 8 app at `~/Code/piggybank` that replicates the Cyfrin piggy_bank Anchor dapp (time-locked SOL savings) using the full solrengine gem stack. Styled and structured like the WalletTrain showcase app. This serves as the first real-world test of `solrengine-programs`.

## Proposed Solution

New Rails 8 app with:
- **Wallet auth** via `solrengine-auth` (SIWS)
- **Lock/unlock SOL** via `solrengine-programs` (generated from piggy_bank IDL)
- **List user's locks** with real-time updates via `solrengine-realtime`
- **WalletTrain-style UI** — dark theme, Tailwind, Turbo Streams, Stimulus

### Pages

1. **Landing** — Hero + connect wallet CTA
2. **Login** — Wallet connect + SIWS sign (reuse WalletTrain pattern)
3. **Dashboard** — List of user's Lock accounts with status, balance, expiration
4. **Lock** — Form: amount (SOL) + duration (minutes) → lock instruction via wallet
5. Each lock shows an **Unlock** button when expired

#### Phase 4: Lock Form — Lock SOL

Build the form to create a new lock.

**Important: Lock keypair requirement.** The piggy_bank `lock` instruction requires a **fresh keypair** for the lock account (it's a `signer`). The client must generate this keypair and include it as an additional signer in the transaction. This means the Stimulus controller handles more of the transaction building than the typical "server builds, client signs" pattern.

**Approach:** The Stimulus controller generates a lock keypair client-side, then calls the server for blockhash + instruction data encoding. The server builds the Borsh-encoded instruction data (discriminator + amt + exp) and returns it. The client constructs the full transaction with both the lock keypair signer and the wallet signer, then uses wallet `signAndSendTransaction`.

- [ ] Lock form partial: amount (SOL, presets: 0.1, 0.2, 0.3) + duration (presets: 2, 5, 10 minutes)
- [ ] `LocksController#build_lock` — server-side:
  - Receives amount_sol and duration_seconds from form
  - Converts SOL to lamports, computes expiration timestamp
  - Builds `PiggyBank::LockInstruction` instruction_data (Borsh-encoded)
  - Fetches blockhash
  - Returns JSON: `{ instruction_data (base64), accounts, blockhash, last_valid_block_height }`
  - **Does NOT include lock account in accounts** — client generates that
- [ ] Stimulus controller (`piggy_bank_controller.js`):
  - Generates fresh `CryptoKeyPair` for lock account
  - Calls `build_lock` endpoint with form params
  - Constructs transaction: fee payer (wallet), lock account (generated keypair as signer), instruction with server-provided data
  - Wallet signs and sends (lock keypair signs too)
- [ ] Success state: show transaction signature with Explorer link
- [ ] After successful lock, refresh dashboard to show new lock

**Success criteria:** Can lock devnet SOL via the form, see the new lock appear on dashboard.

#### Phase 5: Unlock — Unlock Expired Locks

Build the unlock flow.

- [ ] Unlock button on each expired lock card
- [ ] `LocksController#unlock` — builds unlock instruction data:

## Technical Considerations

### Lock Account Keypair (Client-Side Generation)

The piggy_bank `lock` instruction requires a fresh keypair for the lock account. This keypair:
- Is generated client-side in the browser
- Signs the transaction as an additional signer (alongside the wallet)
- The public key becomes the lock account address
- The private key is NOT stored — it's only needed for the initial creation transaction

In the Next.js version, this uses `Keypair.generate()` from `@solana/web3.js`. In our Stimulus controller, we'll use `@solana/kit`'s `generateKeyPair()` which returns a `CryptoKeyPair`.

### Query Filter Offset

The Lock account has discriminator (8 bytes) + dst (32 bytes pubkey) + exp (8 bytes u64). To query locks by destination wallet, the memcmp filter offset is **8** (after discriminator), matching the `dst` field.

### No Token/Transfer Models Needed

Unlike WalletTrain, this app doesn't need `solrengine-tokens` (no SPL token portfolio) or `solrengine-transactions` (no SOL transfer tracking). Lock/unlock operations are entirely program-based, tracked on-chain, not in the local DB.
